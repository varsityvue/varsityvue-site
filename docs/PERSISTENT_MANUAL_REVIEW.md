# Persistent manual review — local Phase 1 candidate

`/internal/data-ingestion` is private staging for schedule, roster, core GameStats and underlying-class corrections. `/internal/stats-import` and its existing format/validation APIs remain unchanged. Approval means accepted for **interim manual export**, never canonical publication. No ingestion code writes schedules, scores, rosters, public stats, Pick ’Em or Team Feed.

## Disposable local operation

Use the existing generated `supabase/config.toml`, Docker and Supabase CLI (installed outside npm). Only `supabase start` and `supabase db reset --local` are needed; never link, push or reset a remote database. The proposed migration follows all existing migrations. Existing repository migrations seed the disposable database's canonical fixtures; ingestion must leave those fixtures unchanged.

Run with `ENABLE_INTERNAL_TOOLS=true`, `NEXT_PUBLIC_SUPABASE_URL` pointing to loopback, the disposable local publishable key in `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`, and the disposable local service key in server-only `INGESTION_LOCAL_SERVICE_KEY`. Read local CLI status into process memory; never print or commit these values. The candidate rejects non-loopback configuration. Keep every shared application Supabase client explicitly configured locally too; do not inherit its remote fallback.

No application dependency or lockfile change is required. Browser verification uses Playwright 1.63 installed under `/tmp/vv-phase1-browser-tools`, outside this package. Run:

- `node --import tsx --test lib/ingestion*.test.ts`
- `node scripts/test-ingestion-local.mjs` after a clean disposable rebuild (creates local-only test users)
- `node scripts/test-ingestion-races.mjs` after the first integration suite
- `node scripts/test-ingestion-browser.mjs` with the local dev server on loopback port 3100

The scripts assert the CLI API is `127.0.0.1`; browser requests are restricted to loopback. Disposable test account passwords remain in a mode-0600 `/tmp` fixture file and are not printed. Test results and screenshots are written under `/tmp`, without API credentials.

## Authorization and persistence

Existing active-account checks and admin/moderator roles govern access. Those roles have global internal review scope consistent with current roster moderation. Contributor school assignments grant no ingestion capability; coach-only, ordinary member, anonymous, suspended and missing-status users are denied. Moderator draft approval grants no new canonical publication authority.

Actor/creator/owner UUIDs are retained audit identifiers rather than profile foreign keys, so existing account deletion is neither blocked nor allowed to cascade into review history. Four private tables store immutable submission scope, retained sources, versioned normalized drafts/validation/source snapshots, and append-only decision/export events. RLS is enabled; direct table and sequence privileges are revoked, including from the service role. An authenticated, security-definer read RPC checks active roles. Only the trusted server's service role can call the mutation RPC. Server actions derive actor from authenticated access, validate canonical schools/contracts/catalogs, and never accept browser role, creator or reviewer identity. The database rechecks active role and derives audit times.

Every mutation locks the submission and compares expected revision/hash. State changes also advance revisions. Creation derives stable private submission/source/initial-row IDs from the actor and request UUID, so a duplicate creation request cannot create a second submission. A request UUID binds actor, command, expected tokens, payload and reason; a mismatched retry fails. Draft/source edits clear approval. Rejected work requires an explicit reasoned reopening; deleting evidence does not reopen it. Readiness/approval requires current validation and all finalized source objects, with no pending reservation. Historical approval retries cannot authorize stale exports. Updates/deletes of revision/event history fail even for privileged accidental writes.

Corrections preserve target, captured current values, reason, differences and expected canonical revision. Static profiles and managed roster records retain distinct identities; explicit public links bridge them. Managed roster UUIDs never become public player IDs. A single authenticated catalog RPC captures managed-roster rows and their database fingerprint; readiness/approval/export take a short share lock and compare that fingerprint to prevent a catalog-change race. Changed canonical target values/status/revision or changed catalog validation block acceptance. Critical unresolved identities and affected-stat reconciliation conflicts block readiness. Missing optional values stay missing; zero remains supplied zero. Required unresolved statistical row metrics cannot be normalized into fabricated lines.

## Evidence and exports

Text (30,000 characters), bounded original JSON/CSV (256 KB), structured form representations and private images are retained for manual transcription. JSON/CSV use Phase 0 adapters. Review uses typed fields and explicit matching; raw JSON is retained as source or captured-baseline detail.

`ingestion-evidence` is a dedicated private bucket. JPEG/PNG/WebP files are limited to 5 MB, 40 million decoded pixels, 10,000 pixels per dimension, one image/frame, and three active/reserved images per submission. Sharp checks actual encoding against claimed MIME, decodes the image and creates an oriented, metadata-stripped WebP preview. Originals remain private and unchanged. A bounded, same-origin multipart route supports the full image limit without changing shared Server Action limits. Paths are fixed server reservations owned by the uploading account; no overwrite/upsert is permitted. Duplicate original hashes within a submission are rejected before reservation and a database unique index prevents finalization races from retaining two identical images.

Authorized preview is a cookie-authenticated streaming route with `private, no-store`, explicit image MIME, `nosniff` and no permanent public/signed URL. Storage RLS also protects private reads. Failure and retention cleanup tombstone source metadata first, retain history and invalidate review; exact server-derived object paths are then deleted through the trusted local cleanup client. Authenticated Storage removal can silently filter tombstoned objects because their read policy denies access, so the server cleanup path is deliberately used and tests assert actual object absence. Failed cleanup can be retried through the reasoned tombstone control. No automatic retention job or unapproved retention duration is enabled.

Export checks exact approved revision/hash, current reproducible validation/catalog and retained objects, then records an immutable export event with submission/class, approved snapshot, source snapshot, actor and server time. Schedule/roster output is clearly interim manual data. Statistics include the existing GameStats manual-insertion marker for format compatibility; this does not publish or grant publishing rights. Export JSON is a controlled internal download, not a permanent public evidence URL. Approval/export never generates commits or PRs.

## Remaining limitations

This candidate intentionally runs only against disposable local Supabase. Production configuration, permissions, migrations and publication require separate authorization. There is no AI, OCR, provider, PDF/XLSX extraction or coach portal. Image validation is not malware scanning; no antivirus/CDR service is integrated. Original metadata is preserved privately as evidence, while previews strip it. Retention is manual and audited; original historical source bodies/snapshots are retained for audit integrity, so physical privacy erasure needs a separately approved policy. There is no automatic orphan sweep; pending/failed reservations appear in the reviewer source list and can be cleaned up explicitly. Reviewer inbox/history pagination and operational rate limiting should be assessed before a production release. Required manual statistics with no compatible public identity link remain blocked rather than silently inventing canonical identity mappings.


## Independent review corrections (F1–F4, October 7, 2026)

Manual schedule dates must fall within August 1–December 31 of the selected football season. Wrong years and spring dates block readiness/approval. The current schedule draft model has no winter/spring or conflict-override field; such dates must be corrected within this supported window rather than accepted through a free-text decision reason. Kickoff TBD remains an absent value, never midnight.

School commitments conflict on the same known date **or** the same known week independently of the opponent, within a submission and against non-bye effective canonical games. Canonical timestamp kickoffs are converted to America/Chicago dates; date-only kickoffs remain dates. The canonical game being corrected is excluded from its own conflict comparison; other commitments still block. A legitimate rematch on a different date/week remains possible. Shared week-zero scrimmages are conservatively surfaced as conflicts because this manual model has no explicit occurrence/phase override. No schedule authority is changed.

Known jersey strings are compared by normalized numeric identity (`00` and `0` collide) without changing the stored strings. Unknown/omitted/unavailable values never participate as zero. Sharing is reported as a visible warning within drafts and against scoped public profiles/active managed rosters. Explicitly linked representations of the corrected identity are excluded from self-conflicts. Inactive managed records and other schools/seasons do not participate. Legitimate shared numbers remain reviewable; the existing readiness/approval decisions require a server-recorded disposition reason. There is no automatic jersey-number prohibition or canonical roster write.

Creation retains an immutable in-memory FormData snapshot and request key for the lifetime of the mounted new-submission form. A lost/uncertain response locks input editing and offers **Retry original creation** using those exact inputs, including original file bytes. Recovery runs after active reviewer authorization: the server-derived actor/request submission ID, creator and stored creation-input hash must match. The input hash includes the selected scope, original form strings, source acknowledgement and optional file name/type/size/bytes hash. A committed creation is recovered before re-reading changed catalog inputs, without another mutation. Different inputs with the same key are rejected. Concurrent initial requests retain the database's existing row lock/request-payload checks.

A definitive pre-mutation validation failure permits editing and a fresh attempt. Once an outcome is uncertain, even a subsequent validation/recovery error keeps the original key and frozen inputs. Edits occur in the recovered submission using existing revision/hash checks. The snapshot is deliberately not written to browser storage: closing/reloading the page discards it; use the inbox to locate a possibly committed submission before starting another. This limitation is visible in the uncertain-outcome message. No automatic retries or new publication capability are introduced.

Validator version is now `vv-manual-review-2`; older saved validation must be saved/reviewed again before readiness/approval/export. The proposed migration, grants/RLS, evidence boundaries and Phase 0 contracts are unchanged.
