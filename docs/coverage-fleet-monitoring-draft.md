## Exact persistence contract

Dedicated Redis namespace `coverage:fleet:v1:`; no client-supplied keys. No payload, geography, coordinates, identity, IP, raw error, request ID, instance ID, event table, trace, delivery ledger or free-text cause. Time is operational UTC, not a visitor timestamp. `revision` is a singleton operational concurrency version, never a request identifier.

Bucket hash `b:<floor(UTC epoch seconds/300)>`, exactly five fields: `accepted`, `database_failure`, `capacity_failure` (integer 0..1,000,000), `indeterminate` (0/1), `finalized` (0/1). Redis derives current time with TIME. Record operations admit current window or previous window strictly before its end+30 seconds. Finalized/evaluated windows reject writes. Counter reaching the cap marks uncertainty; never silently wrap. Bucket expiration is its window end+86,400 seconds, not a sliding expiration. Evaluator materializes empty finalized buckets so a subsequently missing finalized recovery bucket is detectable. At most approximately 291 bucket hashes can exist under the write/evaluation time bounds. Unexpected eviction of a not-yet-finalized bucket cannot be distinguished from no traffic: no-eviction, persistence/reset and access controls are provider gates, not assumed safeguards.

Singleton hash `state`, exactly eleven numeric fields: `last_window`; `failure_streak`, `capacity_streak` and `clean_windows` (0..2); `incident` bit mask (1=ingestion threshold, 2=capacity threshold, 4=indeterminate); `revision`; `notified_revision`; `notify_after`; `lease_until`; `transport_fault` (0/1); `last_eval` (UTC operational epoch seconds). No rolling incident history. This fixed-size state persists without bucket TTL: an incident must not silently expire into health. Versions and epoch values are safe integers in application responses. Redis loss/reset initializes incident=4, transport_fault=1, clean_windows=0; commissioning requires manual review. Revision increases only on incident mask change or authenticated recovery, bounded at 1,000,000,000. Reaching the bound forces indeterminate; recovery refuses exhausted revisions rather than wrap. A deployment/restore must never initialize a clean state as proof of health.

Atomic Lua scripts combine increments/expiry and central decisions. All touched keys are passed explicitly to EVAL. Only server-derived bounded keys and fixed scalar deltas enter Redis; credentials are authorization headers, never command/query URLs. Wrong key types, invalid results, oversized response or clock mismatch sanitize to unavailable. Redis scripting is atomic for concurrency, but not a transaction rollback mechanism for arbitrary runtime errors; dedicated untouched key types and bounded validated arguments are required. Script errors are uncertain, never successful health evidence.

## Collection, flush lifecycle and loss

The existing ingestion callback supplies a fixed category only after enabled, validated, approved database delivery. Disabled, malformed, unapproved, origin/content-type failures and process-budget rejections do not count. Database `54000` maps to capacity_failure; other actual database delivery failures map to database_failure. The SQLSTATE parser is unchanged; raw diagnostics never enter monitoring.

Requires both `COVERAGE_DEMAND_INGESTION_MONITOR_ENABLED=true` and the new `COVERAGE_DEMAND_FLEET_MONITOR_ENABLED=true`. Both are absent/off. Each process owns at most two window deltas and one scheduled `after` task. Observe synchronously increments only the category; `after` snapshots/discards up to two deltas before sending. No timer, interval, delayed invocation or external queue is installed. Concurrent events after the snapshot remain bounded in memory and flush on a subsequent observed event after the task finishes; if none arrives, they may be lost. Busy tasks do not multiply request contexts or retain payloads. Every Redis request has a 1.5-second deadline, no retry/redirect, no credentials/referrer forwarding and a 2,048-byte response bound. Two bucket sends plus at most one uncertainty flag call bound one flush to 4.5 seconds of network deadlines after the response. Ingestion, discovery and navigation do not await delivery. Invalid configuration is processed through the lazy adapter and cannot strand the collector's scheduling latch.

Cold termination, execution cutoff, loss before `after`, reset and abandoned pending memory can lose deltas. A commit with a lost acknowledgment is ambiguous: discarded deltas are never replayed, avoiding duplicate counts without adding identifiers. Known loss/rejection attempts an idempotent central uncertainty flag, safe to retry. Successful persistence of that flag clears only process-local pending uncertainty, not the central incident. If all paths are unavailable or the process dies, even uncertainty may be lost. No exhaustive completeness claim is possible under these exclusions. The independent evaluator deadman detects missing evaluation, not invisible loss of an individual batch. Small windows can undercount, and error share can be biased. Manual recovery explicitly accepts this residual loss.

## Central evaluation and no traffic

GET `/api/cron/coverage-demand-fleet` uses exact Bearer CRON_SECRET, rejects query/body, requires explicit fleet enablement and complete configuration, and bypasses member-session refresh. Declares Node runtime/maxDuration=15; effective hosting limits remain a provider gate. No public status endpoint.

Proposed schedule for later review: every minute (`* * * * *`) UTC, not installed. Evaluate only fully closed windows after 30-second grace; finalize each window once. Process at most twelve contiguous pending windows (one hour). Missing singleton, backwards evaluation state, >12-window backlog, >660 seconds since last successful evaluation, missing finalized recovery evidence or saturation latches indeterminate and resets streak/clean proof. Large gaps reconstruct only the newest pair for review and do not claim complete historical detection. Duplicate invocation does not repeat threshold advancement. No ingestion traffic resets consecutive failure/capacity/clean streaks and supplies no ingestion health proof; independent evaluator liveness still operates.

Ingestion incident: two consecutive finalized windows each with >=5 database_failure+capacity_failure and failures >= accepted (>=50% observed category share). Capacity incident separately: >=5 capacity_failure in each of two consecutive windows, regardless of accepted share. Observed successes never clear incident bits. Any failure recorded in an open window also invalidates accumulated clean proof. Healthy instances do not send incident success signals.

## Manual recovery and authentication

GET `/api/coverage-demand-fleet/recovery` is protected by a separate server-only `COVERAGE_DEMAND_FLEET_RECOVERY_SECRET`. Returns only six bounded operational review values: `window`, `incident`, `revision`, `transport_fault`, `clean_windows`, `evaluated_at`. It does not return Redis credentials, source counters, payloads or diagnostics. It is a trusted operational bearer endpoint, not a member/admin account workflow. Access controls for the secret and approved human operators remain a setup gate.

POST on that route requires the same secret, no query and a <=512-byte exact body with a 1.5-second read deadline: `expected_revision`, `reviewed_window` (nonnegative integers), `cause_resolved=true`, `transport_reviewed=true`, `loss_accepted=true`. No free text, owner identity or cause history is stored. Attestations require human review; code cannot independently prove the cause resolved or missing deliveries recovered.

One atomic operation requires unchanged revision, latest finalized window, evaluation within 90 seconds, two adjacent finalized populated accepted>0 zero-failure determinate windows, and no database/capacity/indeterminate observations in remaining open/grace windows. Missing or stale proof returns 409. Clearing resets central transport_fault and increments revision; only this path can queue an incident success notification. New concurrent failure/uncertainty before the atomic decision prevents recovery. Recovery is not inferred from one healthy instance. Subsequent newly occurring failures are evaluated under the same threshold; no claim is made that manual closure predicts future traffic.

## Independent signals, retry and outage

Reuse `heartbeat` for two distinct Healthchecks UUID destinations: evaluator liveness and incident notifications. Configuration rejects identical destinations, avoiding evaluator success clearing the incident check. Both allow only canonical HTTPS hc-ping.com paths, empty POST, no query/fragment/redirect, omitted credentials/referrer and 1.5-second deadline. No /start, body logs, provider management call or provisioning.

Proposed independent evaluator check: one-minute period, two-minute grace, to be provider-verified later. Success means central evaluation/notification processing completed, never ingestion health. Store failure best-effort signals evaluator failure; total absence is independently detectable. Incident notification emits fail for any latched bit and success only following manual recovery. Claims/acks use the singleton revision and a ten-second delivery lease, with a sixty-second retry interval. A false/throw/ambiguous notification leaves notified_revision behind revision; later evaluator invocations retry. Concurrent evaluation can change revision; stale acknowledgment cannot erase the new pending incident. Duplicate notification delivery is possible, bounded; no exactly-once claim. Lost success acknowledgment can be retried as a state signal, not as a counter delta.

If Redis is unavailable, durable incident mutation cannot be guaranteed. The external liveness check is the independent fallback; no adapter can durably write into an unavailable store. When available again, known fault marking or missed-evaluation detection latches uncertainty. A completely invisible short loss remains a documented limitation and requires accepted manual transport review. Real alert delivery, missed-run, failure, recipient rejection and recovery have not been tested; local stubs model signals only.

## Owner-review schema correction

Every production Lua operation validates all existing touched hashes before interpreting contents or mutating keys: exactly eleven singleton fields and five bucket fields, canonical unsigned decimal integers, per-field ranges, safe integer timestamps/windows, positive bounded revision, and notified_revision no greater than revision. Missing, unexpected, malformed, fractional, noncanonical or out-of-range fields return a fixed invalid-store error. Wholly absent state still initializes latched indeterminate; wholly absent buckets remain eligible for the existing no-traffic/finalized-evidence rules. Partial existing hashes are never initialized or silently repaired.

Corrupt hashes remain untouched. Review returns sanitized monitor_unavailable (503), never a healthy snapshot; recovery returns 503 and cannot clear an incident. Evaluation fails without advancing clean proof or last_eval and best-effort emits only evaluator fail. Because fault/claim/ack also validate the touched hashes, corruption can prevent durable uncertainty marking and incident delivery; independent evaluator failure/missed-run is the fallback, not proof of ingestion health. No incident success is emitted. Remediation/restore requires separately authorized operator review; these routes do not repair corrupt state. Bucket checks cover the explicitly touched current-14 through current range; older retained hashes are not scanned globally and cannot supply recovery proof. Whole-key deletion and invisible pre-finalization loss retain the documented limitations.

Disposable actual-Lua/REST corruption fixtures cover partial singleton and finalized/open bucket field loss, extra fields, malformed/noncanonical/fractional numbers and range violations. All central operations and record reject corruption without mutation; evaluator failure signals are local stubs only. Existing commissioning, aggregation, threshold, expiry, notification and manual recovery fixtures remain required. Hosted TIME, durability, eviction, restore, logging and provider safeguards remain unverified.
